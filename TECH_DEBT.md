# Технічний борг

## Міграція книжок, статей і завантажень (2026-10-11)

### Підтверджено під час первинного аналізу дампу `sql_webbooks_com_ua (3).sql`

- У дампі є лише таблиці `wp_posts`, `wp_postmeta`, `wp_terms`, `wp_termmeta` та службові таблиці. Таблиць `wp_term_taxonomy` і `wp_term_relationships` у ньому немає.
- Саме ці дві таблиці потрібні, щоб безпечно визначити: категорію та кількість публікацій у ній, батьківські категорії, прив'язки постів до категорій і мовні зв'язки Polylang. Тому не можна коректно прибирати дублікати Laravel, порожні категорії чи розділяти дані за UK/RU/PL лише за цим дампом.
- У темі критерієм книжки є наявність одного з метаполів: `download`, `download_pcloud`, `download_hubic`, `download_mega`. Публікації без цих полів повинні лишатися статтями.
- У дампі трапляються невалідні значення метаполя `download` на кшталт `webbooks.com.ua`; їх не слід вважати URL для міграції в S3. Повний список треба отримати повторним парсингом дампу.

### Що потрібно відновити або надати перед зміною категорій

1. Повний SQL-дамп, який містить `wp_term_taxonomy` і `wp_term_relationships` (або окремий експорт цих двох таблиць).
2. Після цього підготувати **лише SQL для phpMyAdmin**, без виконання на production:
   - звіт по категоріях, їхніх мовах, кількості публікацій і батьківських зв'язках;
   - окреме рішення для двох Laravel-категорій: об'єднання або рознесення за мовами/деревом;
   - видалення лише категорій з нульовим фактичним використанням, після перевірки перекладів і меню;
   - зв'язування всіх книжок та статей у трьох мовах через наявні механізми Polylang.

### Запланований безпечний процес міграції завантажень

1. Повторно розібрати дамп і зібрати всі валідні URL з чотирьох метаполів завантаження.
2. Створити ігноровану Git папку `temp/` з підпапками `temp/<post_id>/` — по одній на книжку, незалежно від кількості її URL.
3. Створити `temp/download-links.xlsx` з колонками у погодженому порядку: `Post ID`, `Download URL 1`, `Download URL 2`, `Download URL 3`, `Download URL 4`; службові колонки (назва, slug, ключ метаданих, стан) розмістити після них.
4. Після ручного завантаження файлів у відповідні папки погодити параметри спеціального S3-сховища та виконати завантаження.
5. Згенерувати перевірюваний SQL для заміни старих URL у `wp_postmeta` за `post_id` і точним ключем метаданих. Перед production-виконанням обов'язково сформувати `SELECT`-preview та резервну копію.

### Статус

Первинний аналіз завершено, міграція та створення XLSX/`temp/` призупинені на прохання власника сайту. Жодних даних production не змінено.
